## 根本原因

### 架构师的诊断

> "这是典型的'僵尸代码'反扑。我们在上一轮修复中不仅升级了雷达逻辑，还删除了旧的辅助函数 `_get_corrected_depth`。但是，你的**奖励函数** (`reward_navigation_sota`) 依然在私下调用这个已经被判死刑的函数，导致了崩溃。"

**问题分析**：

1. **代码演进历史**：
   - v1.0: 有 `_get_corrected_depth` 函数，观测和奖励都调用它
   - v2.0: 删除了 `_get_corrected_depth`，观测改为直接使用 `sensor.data.ranges`
   - v3.0: 再次删除，观测改为手算距离
   - **问题**: 奖励函数还在调用 `_get_corrected_depth`

2. **为什么会遗漏**：
   - 奖励函数在文件的不同位置（第374行）
   - 观测函数的修复没有全局搜索引用
   - 只关注了观测空间，忽略了奖励空间

3. **架构师原则**：
   > "为了保证代码的稳健性和可维护性，我们不仅要修好这个报错，还要把'计算雷达距离'这个核心逻辑**封装**起来，供观测（Observation）和奖励（Reward）共同调用，避免逻辑重复。"

## 解决方案

### 架构师方案（v4.0）- 封装核心逻辑

**核心思想**：DRY（Don't Repeat Yourself）原则，观测和奖励共享同一套物理计算逻辑

#### 1. 新增核心工具函数

```python
def _compute_raycaster_distance(env: ManagerBasedRLEnv, sensor_cfg: SceneEntityCfg) -> torch.Tensor:
    """
    [Core Logic] 计算 RayCaster 的物理击中距离

    逻辑：Distance = || Hit_Point - Sensor_Origin ||
    返回：原始距离数据 (单位: 米)
    """
    sensor = env.scene[sensor_cfg.name]
    ray_hits_w = sensor.data.ray_hits_w
    sensor_pos_w = sensor.data.pos_w
    vec = ray_hits_w - sensor_pos_w.unsqueeze(1)
    dist = torch.norm(vec, dim=-1)
    max_range = 12.0
    dist = torch.nan_to_num(dist, nan=max_range, posinf=max_range, neginf=0.0)
    dist = torch.clamp(dist, min=0.0, max=max_range)
    return dist
```

#### 2. 复活兼容性接口

```python
def _get_corrected_depth(env: ManagerBasedRLEnv, sensor_cfg: SceneEntityCfg) -> torch.Tensor:
    """兼容旧接口，直接转发给新的计算核心"""
    return _compute_raycaster_distance(env, sensor_cfg)
```

#### 3. 简化观测函数

```python
def process_lidar_ranges(env: ManagerBasedRLEnv, sensor_cfg: SceneEntityCfg) -> torch.Tensor:
    # 1. 调用核心工具获取米制距离
    distances = _compute_raycaster_distance(env, sensor_cfg)

    # 2. 归一化到 [0, 1] (Observation 需要)
    max_range = 12.0
    distances_normalized = distances / max_range

    # 3. 降采样到36个扇区
    num_sectors = 36
    batch_size, num_rays = distances_normalized.shape
    if num_rays % num_sectors == 0:
        depth_sectors = distances_normalized.view(batch_size, num_sectors, -1).min(dim=2)[0]
    else:
        depth_sectors = distances_normalized

    return depth_sectors
```

### 关键改进

1. **DRY 原则**：
   - ✅ 核心逻辑只写一次
   - ✅ 观测和奖励共享同一套计算
   - ✅ 避免代码重复和不一致

2. **兼容性**：
   - ✅ 保留 `_get_corrected_depth` 作为接口
   - ✅ 奖励函数无需修改
   - ✅ 观测函数更简洁

3. **可维护性**：
   - ✅ 核心逻辑集中在一个函数
   - ✅ 未来修改只需要改一处
   - ✅ 代码结构更清晰

## 经验教训

### 1. 代码修改的全局搜索

**错误做法**：
```
只修改了观测函数，没有全局搜索谁在调用旧函数
```

**正确做法**：
```
修改核心函数前，先用 grep 全局搜索所有引用
例如: grep -n "_get_corrected_depth" dashgo_env_v2.py
```

### 2. DRY 原则的重要性

**问题**：
- 观测函数和奖励函数都需要计算距离
- 如果各写各的，容易出现不一致
- 修改时需要改多处

**解决**：
- 封装核心逻辑到 `_compute_raycaster_distance`
- 所有地方都调用这个核心函数
- 修改时只需要改一处

### 3. 兼容性接口的价值

**为什么保留 `_get_corrected_depth`**：
- 奖励函数在调用它
- 修改奖励函数可能影响其他逻辑
- 保留接口作为"适配器"，降低修改风险
