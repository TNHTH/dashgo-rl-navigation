### 问题2: Python脚本未读取 `control_rate` 参数 ⚠️ 严重程度：中

**位置**：
- `real_control.launch:55` - 设置 `<param name="control_rate" value="20" />`
- `sim2real_golden.launch:149` - 设置 `<param name="control_rate" value="20" />`
- `geo_nav_node.py:114` - 硬编码 `rospy.Timer(rospy.Duration(0.05), self.control_loop)`

**问题**：
```python
# launch文件传递了参数
<param name="control_rate" value="20" />

# 但Python脚本中硬编码，没有读取这个参数
rospy.Timer(rospy.Duration(0.05), self.control_loop)  # 0.05s = 20Hz，硬编码
```

**影响**：
- 参数传递无效
- 修改launch文件中的 `control_rate` 不会改变实际控制频率
- 配置不一致

**修复建议**：
在 `geo_nav_node.py` 中读取参数：
```python
self.control_rate = rospy.get_param('~control_rate', 20)
rospy.Timer(rospy.Duration(1.0/self.control_rate), self.control_loop)
```

### 问题4: 观测维度配置可能不匹配 ⚠️ 严重程度：高

**位置**：
- `geo_nav_node.py:80` - 单帧观测维度 82
- `geo_nav_node.py:256` - 观测结构 LiDAR(72) + Target(2) + LinVel(3) + AngVel(3) + Action(2)
- `geo_nav_policy.py:93` - LiDAR维度计算 `self.num_lidar = 216  # 72线 * 3帧`

**问题**：
```python
# 部署节点 (geo_nav_node.py)
self.single_obs_dim = 82  # 72(Lidar) + 2(Target) + 3(LinVel) + 3(AngVel) + 2(Action)
self.history_len = 3
# 总输入 = 82 * 3 = 246

# 策略网络 (geo_nav_policy.py)
self.num_lidar = 216  # 72线 * 3帧
self.num_state = self.num_actor_obs - self.num_lidar
# 预期输入 = 216 + (2 + 3 + 3 + 2) * 3 = 246
```

**潜在风险**：
- 观测拼接顺序必须完全一致
- 历史帧堆叠方式必须一致（Python中使用 `np.concatenate`）
- 维度计算必须匹配

**验证建议**：
1. 在部署节点中添加维度检查
2. 在模型推理前打印输入shape和预期shape
3. 添加断言检查

### 问题5: LiDAR降采样配置不一致 ⚠️ 严重程度：中

**位置**：
- `geo_nav_node.py:79` - `self.lidar_dim = 72`
- `dashgo_config.py:210` - `data_points_per_scan: int = 720` (实物)
- `dashgo_config.py:211` - `sim_channels_v6: int = 360` (仿真)
- `dashgo_env_v2.py` - 未知（需要检查环境配置）

**问题**：
```
实物LiDAR: 720点/圈
仿真LiDAR: 360点/圈 (v6.0)
部署节点: 72维 (降采样到训练时的维度)
```

**影响**：
- 降采样算法在 `geo_nav_node.py:process_lidar()` 中使用Min-Pooling
- 需要确认训练时也使用相同的降采样方式
- 否则会导致Sim2Real性能下降

**验证建议**：
检查 `dashgo_env_v2.py` 中的LiDAR配置，确认：
1. 仿真中LiDAR的原始维度
2. 降采样方式是否与部署一致（Min-Pooling vs 等间隔采样）

### 问题7: 控制频率不匹配风险 ⚠️ 严重程度：中

**位置**：
- `geo_nav_node.py:114` - 20Hz控制循环 (`rospy.Duration(0.05)`)
- `dashgo_config.py:163` - `ros_control_rate: float = 10.0` (Hz)
- `dashgo_config.py:165` - `isaac_control_dt: float = 0.1` (s = 10Hz)

**问题**：
```
部署节点控制频率: 20Hz (0.05s)
ROS base_controller频率: 10Hz (配置文件)
Isaac Lab控制周期: 10Hz (0.1s)
```

**影响**：
- 部署节点发送控制命令的频率(20Hz)高于底层控制器频率(10Hz)
- 可能导致命令堆积或不一致性
- 需要确认实际机器人底盘的控制频率

**验证建议**：
1. 检查实车 `dashgo_bringup` 配置中的控制频率
2. 对齐部署节点频率与底层控制器频率
3. 或添加缓冲队列处理高频命令

### 问题8: 加速度限制不一致 ⚠️ 严重程度：中

**位置**：
- `geo_nav_node.py:291-292` - 软件限制 `MAX_ACCEL_LIN = 0.05`, `MAX_ACCEL_ANG = 0.1`
- `dashgo_config.py:31-32` - `max_lin_acc: 1.0`, `max_ang_acc: 0.6`

**问题**：
```
部署节点软件限制:
  线加速度: 0.05 m/s² (每控制周期@20Hz = 1.0 m/s²)
  角加速度: 0.1 rad/s² (每控制周期@20Hz = 2.0 rad/s²)

配置文件中的物理限制:
  线加速度: 1.0 m/s²
  角加速度: 0.6 rad/s²
```

**分析**：
- 部署节点的每个控制周期限制看起来是合理的
- 但角加速度累计值(2.0 rad/s²)超过了配置文件(0.6 rad/s²)
- 可能导致部署时过于激进

**验证建议**：
检查加速度计算是否正确：
```python
# 当前代码 (geo_nav_node.py:291-300)
MAX_ACCEL_LIN = 0.05  # m/s² per control cycle at 20Hz
MAX_ACCEL_ANG = 0.1   # rad/s² per control cycle

# 如果这些是"每周期"的增量：
# 实际加速度 = 0.05 * 20Hz = 1.0 m/s² ✅ 匹配配置
# 实际加速度 = 0.1 * 20Hz = 2.0 rad/s² ❌ 超过配置(0.6)
```
